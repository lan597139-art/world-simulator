# T081 数据差异清单（现有实体与关联数据审查）

- 审查日期：2026-11-09
- 审查对象：`world-simulator` 现有 SQLite 库、`backend/models.py`、`backend/migrations/m001–m010`
- 依据文档：`开发2.md` 第八节 T081（审查现有实体和关联数据）、`世界树开发进度.md` 第十节 T064

## 一、结论摘要

1. 世界树八个一级分支（世界基础、世界规则、时空结构、地理结构、文明与社会、组织结构、人物与群体、资源与经济）在数据库中均已有落点表，T064–T080 的模型层已闭环。
2. 开发2 的目标表中，`relationships`、`relationship_types`、`character_appointments`、`group_memberships`、`resource_holdings`、`resource_transactions`、`rule_scopes`、`events`、`state_histories`、`event_relations`、`character_event_perceptions` 均已存在。
3. 实际库共 **32 张表 + 1 个视图**，没有发现与设计文档完全冲突的表；差异集中在“合并实现”“视图替代表”“少量未建表”“新旧字段并存”四类。
4. 不存在必须重建数据库的理由；后续只需补兼容说明与少量增量迁移。

## 五、差异明细

### D1 事件参与方与影响对象合并为 `event_entities`

- 设计：`event_participants` 与 `event_impacts` 两张表。
- 实际：单表 `event_entities`，用 `category`（participant/impact）区分，并有 `participant_role`、`impact_type`、`impact_level`、`is_confirmed`、`description`。
- 影响：API 已按语义拆分（`/events/{id}/participants`、`/events/{id}/impacts`），前端无感知；不影响验收标准。
- 结论：接受，需在数据字典中标注为“合并实现”，避免后续重复建表。

### D2 `relationship_histories` 是视图而非独立表

- 设计：独立历史表。
- 实际：`m004` 创建的兼容视图，数据来源 `state_histories`（`entity_type='relationship'`）。
- 影响：写入仍走 `state_histories`，无重复事实；查询接口 `/relationships/{id}/history` 正常。
- 结论：接受，符合“关系变化必须有历史”的验收；文档需注明“视图”。

### D3 未建 `organization_locations`

- 设计：组织与地点专用关联表。
- 实际：总部用 `organizations.headquarters_location_id`；租用、控制、占领等走通用 `relationships`。
- 影响：可满足关系网络展示，但缺少“组织—地点”专用外键约束与业务校验。
- 结论：V1.0 可接受；若后续组织地点关系复杂化，再增量建表。

### D4 未建 `social_institutions`、`calendar_units`、`world_spatial_settings`

- `social_institutions`：制度暂由 `societies.government_form` 与 `world_rules` 表达。
- `calendar_units`：时间单位暂存于 `time_settings.config` JSON。
- `world_spatial_settings`：空间设置暂存于 `worlds.settings`、`worlds.map_image_url` 与 `locations.coordinates/environment`。
- 影响：不阻塞现有页面；但制度、历法单位、空间测量规则无法独立查询与关联。
- 结论：列入 V1.1 候选，不在本次范围内强行新建。

### D5 未建 `resource_histories`

- 实际：资源数量/状态变化写入 `state_histories`（`entity_type='resource'`），交易写入 `resource_transactions`。
- 影响：满足“资源变化保留来源”，但缺少资源专用历史视图。
- 结论：接受；可后续补 `resource_histories` 兼容视图。

### D6 新旧字段并存带来的重复维护风险

| 位置 | 旧字段/旧结构 | 新结构 | 风险 |
|---|---|---|---|
| events | `participants`、`affected`（JSON 数组） | `event_entities` | 同一参与事实可能两处维护 |
| relationships | `history`（JSON 列） | `state_histories` / 视图 | 历史可能双写 |
| locations | `x`、`y`、`terrain`、`climate`、`nation`、`geo_type` | `parent_location_id`、`location_type_id`、`coordinates`、`environment` | 同一地理属性两套字段 |
| worlds | `createdAt`、`updatedAt`（驼峰） | 其他表统一 `created_at`、`updated_at` | 命名不一致，易写错 |

- 现状：`events.participants/affected` 与 `relationships.history` 属历史兼容列，当前 API 以新结构为准。
- 建议：写入端只写新结构；读取端保留兼容；在 V1.1 迁移中回填后移除旧列。不得在旧列上新增业务逻辑。

### D7 命名与类型约定差异

- `worlds` 使用 camelCase 时间列，其余表为 snake_case。
- `relationships` 的 `source_type`/`target_type` 允许为空（历史数据），服务层需按端点归属推断。
- 多态关联（`source_type + source_id`、`event_entities.entity_type + entity_id`）无数据库外键，依赖服务层校验，符合开发2 §3.5 的技术说明。

## 六、迁移与后续动作

1. **不重建数据库**：现有 32 表已覆盖世界树与开发2 的模型需求。
2. 保持 `state_histories` 为唯一历史写入点；`relationship_histories` 继续作为视图。
3. 事件参与方/影响对象统一写 `event_entities`，不再扩展 `events.participants/affected`。
4. 组织—地点关系暂用 `relationships` + 总部外键；若出现“租用/占领/管辖”强业务约束，再评估专用表。
5. V1.1 候选增量（不影响当前验收）：
   - `social_institutions`、`calendar_units`、`world_spatial_settings`
   - `resource_histories` 兼容视图
   - 旧列回填与清理（events.participants/affected、relationships.history、locations 扁平字段）
6. 迁移脚本编号从 `m011` 起，必须附带回滚说明与测试。
