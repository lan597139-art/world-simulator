## 1. 审计目标与方法

回答两个问题：

1. **全局设置能否从 Tokens 一贯传递到业务页面**——设置改了，业务页面真的变了吗？
2. **特殊组件是否绕过统一体系**——有没有组件自搞一套，不消费令牌？

方法分四层，互相印证：

- **静态扫描**：解析全部 CSS 规则，统计颜色 / 字号 / 间距 / 圆角 / 阴影的硬编码与令牌引用，定位"定义了令牌但没人用"的断点。
- **动态实测**：通过真实设置接口（`PATCH /api/settings`）与外观本地存储，逐个切换全局设置，用 CDP 读取业务页面**实际计算样式**，验证设置是否真正到达渲染结果。
- **跨页档位验证**：在 6 个业务页上逐档切换玻璃 / 字号 / 密度 / 主题，确认修复在全站业务页稳定成立。
- **双引擎回归**：Chrome（CDP）与 Safari（WebDriver）在七档视口 × 6 个中心页上做视觉基线比对。

## 2. 全站令牌继承链模型

全局设置经四层传递到业务页面：

```
① 设置源          ② 载体（<html> 属性 / 内联变量）   ③ 令牌层            ④ 消费层（业务页面）
─────────        ──────────────────────────────      ──────────        ──────────────────
偏好(服务端)  →  data-theme / data-density        →  --text-*        →  业务 CSS var()
偏好(服务端)  →  data-font-size                    →  --ws-space-*    →  业务 CSS var()
偏好(服务端)  →  data-reduce-motion / data-motion  →  --leading-*     →  body / p
本地外观       →  data-skin                        →  --ambient-*     →  #app-background
本地外观       →  data-glass                       →  --glass-*       →  backdrop-filter
本地外观       →  data-text-custom / scopes       →  --text-main 等  →  业务文本
本地外观       →  内联 CSS 变量（--ws-*）          →  --ws-text-*     →  业务文本
```

- **① 设置源**：`SettingsPreferences`（`src/api/settings.ts`）+ 本地外观（`localStorage['ws.ui.appearance']`，`src/utils/appearance.ts`）。
- **② 载体**：`applyExperience()`（`src/utils/experience.ts`）把偏好写到 `<html>` 的 `data-*`；`applyAppearance()` 把外观写到 `<html>` 的 `data-*` 与**内联 CSS 变量**。
- **③ 令牌层**：`src/index.css`、`src/styles/design-system.css`、`src/styles/appearance-studio.css` 三个文件定义全部令牌。
- **④ 消费层**：24 个业务/组件 CSS 文件 + TSX。

继承审计的核心，就是检查 **②→③→④** 每一跳是否真的接通。

### 4.3 玻璃档位断裂的根因

`--glass-blur` 确实被业务页消费（`design-system.css:129-130`、`index.css:352-353` 的 `backdrop-filter`），但存在**双重写入冲突**：

- `applyExperience()` 依据本地 `ws.ui.glass` 设置 `html[data-glass]`；
- `index.css:311-313` 据此定义 `--glass-blur`（低 14px / 高 56px / 实心 0px）；
- **但** `applyAppearance()`（`src/utils/appearance.ts:583-584`）用 `root.style.setProperty('--glass-blur'/'--glass-opacity', …)` **内联覆盖**。

内联样式优先级高于同元素的样式表规则，因此 `data-glass` 的 `--glass-blur`/`--glass-opacity` 被彻底遮蔽，**玻璃档位对模糊与透明度完全失效**。`--glass-saturate` 因外观系统未内联写入，才幸免生效。

**修复（本轮已实施）**：改由 CSS 档位规则作为唯一取值来源，外观系统在档位生效时不再内联遮蔽——

- `src/utils/appearance.ts`：新增 `resolveGlassTier()`（优先 `<html>` 的 `data-glass`，兜底读 `ws.ui.glass`）；`applyAppearance()` 在档位为低 / 高 / 实心时 `removeProperty` 掉内联的 `--glass-blur`/`--glass-opacity`，交回 CSS；仅"标准"档（无档位属性）时写入外观自定义值。
- `src/index.css`：补全档位规则的透明度取值（低 / 高 `--glass-opacity: 1`），与既有预设一致，使 CSS 成为档位的单一来源。

修复后 6 个中心页 × 3 档位复测全部正确（见 §4.2），且默认"标准"档取值不变，设计台既有行为不受影响。

### 4.4 字号档位断裂的根因与修复

`html[data-font-size="small"|"large"]`（`design-system.css:195-196`）覆盖 `--text-3xs/2xs/xs/sm/base/lg`，但 `applyAppearance()` 会把 `--text-base/sm/xs/lg`（以及 `xl` 以上）**内联**写入——内联优先级高于样式表规则，于是字号档位对正文尺度完全失效，只有未被内联的 `--text-2xs/3xs` 能响应。实测：`medium/large/small` 三档下 `--text-base` 恒为 15px、`--text-sm` 恒为 13px。

这与玻璃档位是**同型缺陷**（偏好设置被外观内联值遮蔽），修复方式一致，并额外处理了时序：

- `src/utils/appearance.ts`：抽出 `applyPreferenceTokens()`，先用外观值打底写入玻璃与字号阶，再按当前生效档位 `removeProperty` 掉被档位规则覆盖的令牌（玻璃 `--glass-blur/opacity`；字号 `--text-xs/sm/base/lg`），交回 CSS；`applyAppearance()` 末尾调用。
- `src/utils/experience.ts`：`applyExperience()` 写入 `data-font-size` 等偏好后同样调用 `applyPreferenceTokens()`。首次加载时 `applyExperience` 晚于 `applyAppearance`，只靠 `applyAppearance` 无法覆盖"偏好后到"的路径；两处共同调用保证首次加载、切换页面、改动偏好三条路径一致。

修复后三档实测（见 §4.2）：`large` 16/13.5/12/18.5px、`small` 13.5/11.5/10/16px，与 `design-system.css` 档位规则逐字一致；`medium` 档外观自定义值不变。`--text-xl` 以上不在档位规则覆盖范围内，仍由外观自定义字号派生。

### 4.5 外壳字号硬编码的根因与修复（本轮新增）

`creation-center.css` 在 `src/App.tsx:4` **全局引入**，其 `.cc-*` 外壳类（侧栏、顶栏、面包屑、头像、搜索框等）在**全部 6 个业务页**渲染。其中 7 处字号为硬编码像素值，不消费 `--text-*` 令牌，因此**全局字号设置对全局外壳完全无效**——外壳与页面正文的字号尺度脱节，是字号设置抵达业务页面的最后一处跨页缺陷。

**修复（本轮已实施）**：将 7 处外壳硬编码字号映射到令牌——

| 选择器 | 原值 | 改为 | 依据 |
| --- | --- | --- | --- |
| `.cc-brand-copy strong` | 16px | `var(--text-lg)` | 品牌名强调文本，对应 `--text-lg` |
| `.cc-nav-label` | 10px | `var(--text-xs)` | 导航分组标签，`design-system.css` 已为该选择器定义 `var(--text-xs)` |
| `.cc-nav-item` | 12.5px | `var(--text-sm)` | 与 `--text-sm` 精确相等 |
| `.cc-breadcrumb` | 11px | `var(--text-xs)` | 与 `--text-xs` 精确相等 |
| `.cc-search input` | 11.5px | `var(--text-sm)` | 与全局 `input { font-size: var(--text-sm) }` 一致 |
| `.cc-avatar` | 11px | `var(--text-xs)` | 与 `--text-xs` 精确相等 |
| `.cc-profile-copy strong` | 10.5px | `var(--text-xs)` | 用户名片强调文本，归入最小可读档 |

修复后实测（`/?page=creation-center`）：`medium` 档 `cc-nav-label=11px / cc-nav-item=13px / cc-avatar=11px`；`large` 档 `12 / 13.5 / 12px`；`small` 档 `10 / 11.5 / 10px`——**7 个外壳选择器全部随字号档精确缩放**，与档位规则逐字一致。

### 7.2 Safari：受阻 ✗

- `safaridriver`（Safari 26.6.2）可启动且 `/status` 返回 `ready:true`；
- 但创建会话时 Safari 拒绝：`You must enable 'Allow remote automation' in the Developer section of Safari Settings`；
- 该开关是 **Safari GUI 专属设置**。本轮最终确认**无免密码命令行路径**：
  - SIP 开启（`csrutil status` = enabled）；
  - `~/Library/Containers/com.apple.Safari` 带 SIP 保护标志（`@`），`Data/Library/Preferences` 对所有者 `a1-6` 亦 `Operation not permitted`（EPERM）；
  - `sudo -n` 需要密码（`sudo: a password is required`），用户虽在 `admin` 组但未提供密码；
  - 写入用户级 `com.apple.Safari.plist` 的 `AllowRemoteAutomation` 被忽略（Safari 读沙盒容器，不读用户 plist）；
  - `safaridriver --enable` 需要交互式密码，`osascript` 无法操作 Safari 菜单栏（返回空、`click` 失败 `-1728`）。

**Safari 回归未能执行。** 需用户手动操作：**Safari → 设置 → 高级 → 开发者 → 勾选「允许远程自动化」**（或以管理员密码执行 `sudo safaridriver --enable`），然后运行：

```bash
python3 .verify/visual_baseline.py capture --engine safari
python3 .verify/visual_baseline.py compare --engine safari
```

（审计过程中对 Safari 偏好与进程的临时改动已全部还原，Safari 已恢复正常运行。若始终无法开启，按约定转为**真实 Safari 人工回归**；Playwright WebKit 仅作辅助，不冒充真实 Safari 验收。）
