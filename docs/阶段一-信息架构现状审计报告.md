## 1. 路由与导航机制现状

### 1.1 路由机制：状态路由，无页面级 URL

- 全站不是 React Router 路由，而是 `src/App.tsx` 内的 `useState<PageKey> activePage` 状态切换（`setActivePage`），页面组件经 `lazy()` 懒加载。
- 唯一的 URL 状态是 `?product=<game|literature|companion|diary|yunbao>` 查询参数（`storeProduct` 写入 localStorage + `history.replaceState`）。
- 后果（信息架构相关）：
  1. **页面无法被直接链接、收藏或分享**（除产品参数外）；
  2. **浏览器返回键不经过页面栈**，返回语义由 `navStack` / "返回产品主页"按钮等自定义逻辑近似模拟；
  3. `CommunitySocialPage` 内部甚至用 `window.location.assign('/?page=community#community-public-works')` 硬拼 URL 模拟跨页跳转，说明页面级 URL 缺失已在影响实现；
  4. 全站 42 个 PageKey 只有一部分在 URL 中可表达，深度链接验收项（需求 1.6"浏览器返回职责"）当前无法满足。

### 1.2 全局导航：双轨定义，已发生漂移风险

全局一级导航存在**两套平行定义**：

| 来源 | 内容 | 消费方 |
|---|---|---|
| `src/components/creation-center/CreationCenterSidebar.tsx` 的 `groups()` | 4 分组 13 项（硬编码，带图标） | **真实渲染**的全局侧边栏（创作中心及全部全局中心页） |
| `src/navigation/navRegistry.ts` 的 `GLOBAL_NAV_GROUPS` | 4 分组 12 项（无图标，声称"侧边栏渲染与面包屑生成的唯一来源"） | 仅 `buildBreadcrumb()` 面包屑 |

- 注释宣称"避免两处漂移"，但侧边栏实际渲染的是 `CreationCenterSidebar`，两套定义只能靠人工同步。
- 侧边栏底部另有：云宝工作台（`canAccessYunbao` 开发者可见）、设置、语言切换。
- `EXTRA_GROUP`（navRegistry 121–132 行）为产品工作区"无父级"页面补分组（世界构建/模拟与推演/写作辅助/人格与记忆/经历与来源/工作区总览/云宝工作台），说明产品工作区内存在大量不在 nav_groups 中的游离页面。

### 1.3 产品工作区导航

- 5 个产品（game 游戏创作 / literature 文学创作 / companion 虚拟角色 / diary 日记与传记 / yunbao 云宝工作台），各带 `nav_groups` 二级分组（世界构建/模拟与推演/数据安全/故事创作/人生记录/经历与来源/长期互动/虚拟角色空间/世界与设定/人物与关系/历程与记录/人格与记忆）。
- 首页态侧边栏显示"四大创作产品"切换（不含 yunbao）；工作区态显示当前产品 nav_groups。
- 云宝有独立白名单 `YUNBAO_VISIBLE_PAGES`（13 页可见）与隐藏黑名单 `YUNBAO_HIDDEN_PAGES`（7 页禁直达）——同一产品内"可见/隐藏"两套名单并存。

### 4.8 本区三条横切结论

1. **创作者资产库 vs 我的作品**：语义边界成立（收纳容器 vs 作品元数据+场景入口），漏点在统计三口径、封面单向写入、两套归档语义——需求 1.4 的"两个模块可以建立关联，但不能简单合并"方向正确，关联缺失而非职责混淆。

1. **同一模块在 4–5 个产品重复注册**，产品差异只靠 modes 配置——功能本体未分层，用户换产品后看到的几乎同一批页面（需求 1.2 要求"按用户目的组织"，当前是按产品组织）。

## 7. 后端商业资源现状（轻审计，服务阶段一映射）

### 7.1 灵果/灵植域（backend/spirit_economy.py + models.py）

| 模型 | 现状 | 与需求差距 |
|---|---|---|
| `SpiritAccount` | **单一 `fruit_balance`**，无来源分类；`developer_exempt` 豁免标记 | 需求 4.2 要求按来源区分账本（充值灵石/可提现灵石/免费灵果/充值兑换灵果/打赏所得灵果）；当前**没有灵石货币**，灵果即唯一软通货，**持有量不携带来源维度** |
| `SpiritPlantType` | 目录含 `world_seed`（建界灵植）与 `oc_seed`（塑人灵植），**种子价均为 60 灵果/株**（`DEFAULT_CATALOG`，站长可改价） | 需求 4.4 确认价：OC 30 灵果/株、世界 100 灵果/株 → **现有种子数据与确认价不符**（60/60），需产品确认迁移策略 |
| `SpiritInventory` | 按 `(user_id, plant_type_id)` 记数量，**无来源维度** | 创建消耗灵植时会丢失来源流水资格（需求 4.7 要求保留来源） |
| `SpiritTransaction` | `kind`（reward/exchange/gift/tip/consume/admin）+ `ref_type`/`ref_id` + `counterparty_user_id` + `balance_after` + `meta` JSON | **交易级分类存在**（kind 可区分奖励/兑换/赠送/打赏/消耗），但这是流水类型而非**持有来源分类**；且缺显式"规则版本"列（需求 4.11） |
| `SpiritRewardRule/Claim` | 站长配置的免费领取规则（注册奖励 120、每日签到 10 等） | 免费来源存在，但领取结果**混入同一余额**，无免费来源子账本 |
| `SpiritOperation` | 幂等记录（user+operation+idempotency_key 唯一） | 满足防重复提交基础 |
| 端点 | `GET /api/spirit/summary` `/transactions`；`POST /api/spirit/exchange`（灵果→灵植）、`/gift`（赠送/打赏）、`/rewards/{key}/claim`、`/consume`；管理端 `/admin/adjust`、`/admin/overview`、`/admin/rewards`(POST/PATCH)、`/admin/plants`(POST/PATCH)、`/admin/transactions`、`/admin/claims` | **无充值端点、无打赏收益反向兑换、无提现端点** |

### 7.2 商业账单域（backend/billing.py + models.py）

- 模型：`BillingAccount.balance_cents`（独立人民币分级账）、`BillingMembership`、`BillingOrder`（创建/支付/取消，沙盒支付）、`BillingLedgerEntry`（`entry_type` 注释枚举：topup/membership/service/ai_usage/creator_earning/refund；正负金额 + `balance_after_cents` + details JSON）、`BillingAiUsage`、`BillingSettlement`。
- 端点：`/api/billing/overview|orders(GET/POST)|orders/{id}/pay|orders/{id}/cancel|membership(PATCH)|usage(GET/PATCH)|records|settlements|settlements/run`。
- 判断：
  1. **billing 域与 spirit 域是两套平行货币体系**（人民币分账 vs 灵果），需求定义的"人民币充值→充值灵石"映射与"打赏收益→可提现灵石"在两侧均不存在；
  2. `entry_type` 枚举中**没有 withdrawal**（`billing.py` grep withdraw 零命中；前端亦自述"提现通道未接入"、收款账户为待接入空态）——提现链路（申请/审核/打款）全站空白；
  3. 创作者收入双轨：灵果打赏（`SpiritTransaction.kind='tip'`）与人民币结算（`BillingSettlement`/`creator_earning`）并存、零互链；
  4. "AI 服务账户"对象全库（backend *.py + src *.ts/tsx）grep 零命中——AI 的账户性配置挂在设置中心 AI 接入设置，`BillingAiUsage` 只是用量流水不是账户对象（符合需求 4.12"会员与 AI 服务不得直接修改灵石/灵果/灵植账本"的方向，阶段四正式确认即可；backend/yunbao.py 中出现的 "withdrawn" 仅为性格标签 key，与提现无关）。

### 7.3 阶段一结论（商业域对 IA 的影响）

- 「账户服务」区两个页面当前映射的后端事实：灵果域（余额+兑换+赠送打赏+奖励+创建消耗+站长后台）与账单域（沙盒充值+订单+会员+AI 用量+创作者结算+流水导出）。**来源分类持有账本、灵石、提现均为空白**，信息架构规划只能先落"目录与职责"，不得虚构余额语义（呼应需求 1.5、4.13）。
- 待确认参数已在需求 4.13 列出；本审计补充两条：
  1. **现有灵植种子价 60/60 与确认价 30/100 冲突**，需产品确认迁移策略（改种子值 or 存量数据迁移）；
  2. 需求 4.12 要求"充值灵石兑换灵果/灵植"等流转——当前灵果域根本没有充值入口，**灵石兑换灵果的比例无现有配置可审计**，属全新参数，列入待确认。

| 9 | **死代码与死数据链路** | 4 个死页面 + ProductSwitcher + 200 行死壳 + PageKey 双定义 + ChatPage 写 `api/diary` 死链路 | 全站 |
| 10 | **超千行单文件页 6 个** | WorldStructure 2273 / CharacterBuilding 2483 / WritingPage 2072 / CreatorAssets 1143 / WorldBuilding 1063 / CommunityPage 1095 | 拆分主工作面 |

**补充结论**：全站**没有一处**已完全达到需求 1.2 的"三级层级 + 单一主归属"标准。最接近的是**社区社交页**（7 tab 收纳）与**商业与服务中心**（6 区目录）——可作为返工模式样板；最远的是内容社区、用户中心、内容商城、JournalPage。

## 9. 审计结论：与目标一级结构的差距

### 9.1 与需求 1.2 目标结构的逐项差距

| 需求目标 | 现状 | 差距等级 |
|---|---|---|
| 一级只分"创作与体验 / 创作管理 / 账户服务" | 已按此分组，但多出"个人空间"组，且 AI/游戏/商城仍是 3 个并列一级入口 | **部分达成**（缺消费体验中心合并） |
| 消费体验中心合并入口（AI+游戏+商城） | 3 个独立一级入口，3 个页面互不共享容器/框架 | **未达成** |
| 创作中心不堆所有专业模块 | 首页 5 场景 + 8 工具 + 3 资产 + 4 作品 = 20 个可点卡 | **未达成** |
| 创作中心 / 资产库 / 作品 三者职责清晰 | 语义边界成立，但统计三口径、封面单向写入、两套归档 | **基本达成，有漏点** |
| 内容社区 vs 社区社交 职责清晰 | 社区社交已 tab 收纳；内容社区仍混排 9 类含社交性"关注动态" | **部分达成** |
| 账户服务目录清楚 | 灵果/商业两页语义清晰但零互链、双账本、admin 混入个人页 | **部分达成** |
| 不把全站功能平铺在同一页面 | 见第 8 节第 3 条 | **未达成** |
| 同一功能单一主归属 | 见第 8 节第 4、7 条 | **未达成** |

### 9.2 三个一级区域的审计判定

1. **创作与体验**：结构最差。合并入口未做、社区页平铺最重、三个体验页都是"创作数据换皮"、10+ 空态占位。返工重点是**新建消费体验中心容器 + 内容社区按内容类型分区**。
2. **创作管理**：结构最接近目标。资产库（三栏工作台）与作品页（hero+网格）职责清晰，需修的是**统计口径统一、封面写入说明、归档语义统一**。
3. **账户服务**：目录与名称基本合理，缺的是**两页互链 + 来源分类账本（阶段四）+ admin 抽离**。账户服务的 IA 改造受制于后端空白，阶段一只能定目录，不能定余额语义。
